# Article House Style

## Purpose

Use this style for all technical learning articles in this repository.

The goal is to make each article feel like a clear, technically mature engineering publication rather than beginner study notes or a generic AI-generated blog post.

## Audience

Write for:
- software engineers
- AI engineers
- QA / test engineers
- technical recruiters
- postgraduate-level readers
- engineers who want a concise introduction to the topic

Assume the reader is technically literate but may not already know the specific topic.

## Tone

Use a professional top 1% enginners, calm and technically mature tone.

Prefer:
- concise explanations
- precise terminology
- practical examples
- clear trade-offs
- engineering reasoning
- diagrams where they improve understanding
- tables where comparison is useful

Avoid:
- excessive storytelling
- motivational filler
- exaggerated claims
- generic introductions
- repetitive definitions
- phrases such as "in today's rapidly evolving world"
- unnecessary buzzwords
- writing that sounds like lecture notes for beginners

## Writing Principle

The article should help the reader build a usable understanding of the topic.

Do not merely define terms.

Show:
1. what the concept is
2. where it fits in a system
3. why it matters
4. how it behaves
5. how it fails
6. how engineers test or evaluate it
7. what trade-offs exist

## Article Structure

Use this structure where relevant:

1. Title
2. Author
3. AI-assisted disclosure
4. Abstract
5. Clickable Table of Contents
6. Core concept / architecture
7. Key terminology
8. Main components
9. System flow or lifecycle
10. Practical examples
11. Failure modes
12. Testing / evaluation approach
13. Case study
14. Key engineering trade-offs
15. One-page summary / memory map
16. Key discussion points
17. Short conclusion
18. References

Not every article must use every section. Remove sections that do not add value.

## Visual Style

Use a restrained engineering-publication style.

Preferred:
- off-white background
- charcoal text
- muted grey / green accents
- subtle borders
- generous whitespace
- narrow comfortable reading width
- simple tables
- minimal diagram styling
- strong information hierarchy
- print-friendly layout

Avoid:
- bright blue
- gradients
- neon colours
- excessive cards
- oversized icons
- flashy UI elements
- decorative visuals that do not explain anything

## Tables

Use tables for:
- terminology
- comparisons
- testing matrices
- trade-offs
- failure modes
- metrics
- architectural responsibilities

Keep table cells concise.

## Diagrams

Diagrams should explain relationships, not decorate the page.

Prefer simple flows such as:

User → Interface → Service → API → Backend

or:

Audio → STT → LLM → Tool Call → TTS

Use clear labels and minimal styling.

## Examples

Prefer realistic technical examples.

When relevant, examples may draw from:
- AI voice agents
- STT / TTS
- LLM applications
- tool calling
- APIs
- regression testing
- cloud systems
- smart contracts
- IoT
- blockchain / DLT
- supply-chain automation

Do not invent confidential company information.

## Author Disclosure

Use:

**Author: Yogesh Sridhar**

**Disclosure:** AI-assisted for structuring, editing and presentation. The ideas, learning, examples, interpretations and conclusions are the author's own.

## Quality Standard

The article should feel suitable for:
- a public GitHub engineering portfolio
- a technical blog
- a postgraduate learning portfolio
- professional discussion with engineers

Before finalising, ask:

- Is the hierarchy clear?
- Is the content technically correct?
- Is any section repetitive?
- Are the examples realistic?
- Does each diagram teach something?
- Are tables concise?
- Does this feel written for engineers rather than students memorising definitions?
- Can a reader explain the topic after reading it?
