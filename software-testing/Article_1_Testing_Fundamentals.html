1 · Core Mental Model

Testing is evidence for a decision

The simplest useful model is not “run tests and find bugs.” It is: identify risk → choose the right test layer → collect evidence → make a release decision.

1. Risk
What can go wrong?
→
2. Test Layer
Where should we test?
→
3. Evidence
What proves it?
→
4. Decision
Ship, fix, monitor?
Engineering mindset: A failed test is useful only if it tells us something actionable: what failed, under which conditions, at which layer, with what business impact, and whether it can be reproduced.
2 · SDLC

At what stage should testing happen?

Modern testing is continuous. Different test activities belong at different stages of the Software Development Life Cycle (SDLC).

SDLC stage Main testing activity Typical techniques Question being answered Your project example
Requirements Requirement review, acceptance criteria, risk analysis Static testing, ambiguity review, threat modelling Are we building the right thing? Define what a voice agent must do before a booking is considered successful.
Design / Architecture Testability and failure-path review Architecture review, security design review, contract design Can this design be tested and operated safely? Map STT → LLM → tool/API → TTS boundaries and failure points.
Development Fast developer feedback Unit, component, static analysis Does each small piece behave correctly? Validate date parsing, booking parameter extraction, smart-contract functions.
Integration Validate interfaces between systems API tests, contract tests, integration tests Do components communicate correctly? Voice agent calls booking API with correct date/time; IoT event triggers contract logic.
System / Pre-release Validate complete behaviour System, E2E, regression, performance, security Does the whole product work under realistic conditions? Real call → speech recognition → booking → confirmation → TTS.
Release Release confidence Smoke tests, deployment verification, canary checks Is the deployed build healthy? Agent answers, tools connect, core flow works after deployment.
Production Observe real behaviour Monitoring, tracing, synthetic tests, incident analysis Is the system healthy for real users? Track call latency, booking failures, STT error patterns and tool-call failures.
Shift left: test earlier to prevent expensive defects.
Shift right: observe real production behaviour to detect issues that pre-release environments cannot fully reproduce.
3 · Test Layers

The test pyramid

The closer a test is to the code, the faster and cheaper it usually is. The closer it is to the full user journey, the more realistic — but slower and more expensive — it becomes.

E2E / UI — few, high-value journeys
Integration / API — system boundaries
Component — business logic in isolation
Unit — many fast checks
Voice-agent example Unit: parse “next Tuesday at 3”.
Integration: LLM/tool request reaches booking API correctly.
E2E: caller speaks → booking created → spoken confirmation.
Smart-contract / IoT example Unit: contract condition evaluates correctly.
Integration: IoT sensor event reaches blockchain layer.
E2E: physical event → smart-contract execution → supply-chain status update.

5 · Functional vs Non-functional

Two categories that prevent confusion

Functional testing

Tests what the system does.

Login Booking Payment Cancellation Smart-contract execution
Non-functional testing

Tests how well the system does it.

Performance Security Scalability Reliability Usability Accessibility
6 · Automation

How testing evolved from the 2000s

Early 2000s
Testing often followed development. Manual test execution, large release cycles, separate QA phases.
2001 onward
Agile increases feedback frequency. Smaller releases, closer collaboration, continuous testing mindset.
Mid-2000s
Browser automation grows. Tools such as Selenium make repeatable UI regression practical.
2010s
CI/CD and DevOps mature. Automated test suites become part of build and deployment pipelines.
Cloud era
Infrastructure becomes dynamic. Testing expands to APIs, distributed systems, containers, resilience and scale.
AI era
Outputs become probabilistic. Evaluation focuses on behaviour, safety, task completion, consistency and tool correctness — not only exact string matching.
Automation principle: automate predictable repetition; keep human judgement for ambiguity, usability, exploration and risk-based investigation.

8 · Security

Security testing terminology

Vulnerability assessment Identify weaknesses and known issues. Often tool-assisted and broad.
Penetration test Authorised attempt to validate whether weaknesses can actually be exploited.
Threat modelling Ask what assets matter, who may attack them, how they could be attacked, and what controls are needed.
TermMeaningMental shortcut
Black boxTester has little/no internal knowledge.External attacker view.
White boxTester has source/design/internal information.Deep internal view.
Grey boxSome internal information is available.Mixed real-world view.
SASTStatic Application Security Testing.Inspect code without running it.
DASTDynamic Application Security Testing.Attack/test the running application.
SCASoftware Composition Analysis.Check third-party dependencies.
CVEIdentifier for a publicly disclosed vulnerability.Which known vulnerability?
CVSSSeverity scoring framework for vulnerabilities.How serious is it?
Red teamSimulates attacker behaviour.Offence.
Blue teamDefends and detects attacks.Defence.
Purple teamRed + Blue collaboration.Improve both.
Security testing must be authorised. A penetration test is not simply “running a scanner”; it is controlled validation of exploitable risk within an agreed scope.

How to isolate a defect

LayerWhat to verifyExample failure

LatencyHow long did the complete turn take?Agent waits 4 seconds before responding.

Representative test scenarios

  • Book a normal appointment — happy path.
  • User changes date halfway through the conversation.
  • User interrupts while the agent is speaking (barge-in).
  • Background noise affects recognition.
  • API fails after the agent already told the user it was processing the request.
  • Agent must not claim success unless the tool/backend confirms success.
  • Prompt update improves one intent but breaks another — regression test.

11 · Practical Test Design

A compact framework for designing tests

Happy path What should work under normal conditions?
Negative path What invalid input should be rejected safely?
Boundary What happens at minimum/maximum limits?
Dependency failure What if an API, database, model or cloud service fails?
State change What if the user changes their mind midway?
Security / abuse What happens when a user attempts an unauthorised action?
Performance Does the feature still work under realistic load?
Observability If it fails, can engineers prove where and why?
12 · Defect Reporting

What a strong bug report looks like

TITLE Voice agent creates 17:00 booking when caller requests 15:00 ENVIRONMENT Staging / Agent build X PRECONDITION Caller has valid customer profile STEPS 1. Call agent 2. Say: "Please book Tuesday at three in the afternoon" 3. Confirm requested slot EXPECTED Booking created at 15:00 ACTUAL Booking created at 17:00 EVIDENCE - STT transcript: correct - LLM extracted time: 15:00 - API payload: 17:00 - Backend record: 17:00 IMPACT Incorrect customer booking LIKELY FAILURE LAYER Tool parameter transformation / timezone handling
Strong testers reduce debugging time by attaching evidence that narrows the failure to a specific layer.
13 · Key Discussion Points

Concepts worth being able to explain naturally

  • Testing is risk-based evidence, not only bug finding.
  • Testing should happen throughout the SDLC, not only after development.
  • Unit → integration → system → E2E represents increasing realism and usually increasing cost.
  • Retest confirms a fix; regression checks that the change did not break other behaviour.
  • Functional tests what the system does; non-functional tests qualities such as speed, security and reliability.
  • Cloud testing must consider distributed failure, scaling, resilience and configuration — not just application screens.
  • Pen testing validates exploitable security risk under authorised scope; it is different from broad vulnerability scanning.
  • Automation is strongest for repeatable checks; human testers remain important for exploration, ambiguity and user experience.
  • AI/voice systems require layer-by-layer diagnosis: STT, model reasoning, tool calls, backend behaviour, TTS and latency.
  • Observability is part of testability. A system that cannot explain its failures is harder and more expensive to validate.
